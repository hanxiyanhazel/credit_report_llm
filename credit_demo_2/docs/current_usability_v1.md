# 当前可用程度（V1）

这份文档用于说明 `credit_demo_2` 当前已经适合怎么用，以及暂时还不建议怎么用。

## 1. 当前适合使用的场景

### A. 单轮、结构清晰的问题

例如：

- 当前未结清账户有多少个？
- 当前未结清账户余额合计是多少？
- 近24个月的逾期账户有多少？
- 最近1个月查询次数是多少？

这类问题当前已经比较适合用于：

- 看 SQL planner 是否能选对表
- 看 SQL 是否按报告日期锚点执行
- 看结果解释是否比旧版 `metric` 路由更自然

需要注意：

- 像“近24个月的逾期账户有多少”这类问法，当前系统默认回答的是 `去重账户数`。
- 如果业务更关注 `账户-月份口径的逾期记录数`，需要在答案里额外澄清，或改成更明确的问法。

### B. 展示层直接提取问题

例如：

- 请按照以下格式提取基本信息
- 请提取身份信息
- 请提取信息概要
- 请提取查询记录概要

这类问题当前已经开始支持独立的 `direct_extract` 链路：

- 先由大模型判断是否属于提取型问题
- 再由程序定位 PDF 前几页对应模块
- 最后由大模型在小范围文本内做字段/模块提取

### B. 少量连续追问

例如：

1. 近24个月的逾期账户有多少？
2. 这些账户都是什么分类，分别多少钱？

当前已经补了最小的结果集承接机制，可用于验证“上一轮账户集合 -> 下一轮分组统计”。

## 2. 当前谨慎使用的场景

### A. 复杂口径强依赖的问题

例如：

- 未结清账户数、余额、借款金额三项混合口径总结
- 查询概要口径和查询明细口径需要同时并列说明
- 信用卡特殊事项需要非常细的业务判断

这些问题不是不能做，而是当前 SQL 版还没有把全部业务口径沉淀成稳定视图或稳定规则。

### B. 多轮追问链特别长的问题

例如：

1. 先问账户数
2. 再问这些账户分类
3. 再问其中小贷机构的余额
4. 再问近15个月同口径结果

当前可以做实验，但还不建议视为稳定产品行为，因为结果集引用机制还只是第一版。

## 3. 当前不建议直接当成产品能力承诺的点

- 任意自然语言都能稳定转成正确 SQL
- 任意连续追问都能稳定引用上一轮结果集
- 所有金额字段语义都已经完全固化
- 所有业务口径都已经和业务方核对完成

## 4. 当前阶段的正确定位

`credit_demo_2` 现在已经可以作为：

- SQL 查询版 demo
- SQL planner / answer generator 的实验场
- 对比旧版 `metric` 路由的验证环境

但还不应直接视为：

- 全面稳定的生产级智能查询方案

## 5. 建议现在的使用方式

先优先拿它验证这三类问题：

1. 单轮高频统计问题是否更自然
2. 少量连续追问是否比旧版灵活
3. planner prompt / answer prompt 拆开后，输出是否更稳定
