# SQL 版规则维护手册（V1）

这份手册用于固定：

1. 以后如果新增一条业务口径补充，应该先改哪里
2. 什么时候改 `agent_loop.py`
3. 什么时候改 `schema_metadata.json`
4. 什么时候改 `sql_runtime.py`

目标是避免规则散落在各处，后续新增提示时可以按统一步骤处理。

## 1. 总原则

新增一条业务规则时，不要先想到“改 prompt 文案”，而是先判断它属于哪一类：

1. **怎么算**
   - 这是指标定义、默认统计口径、默认时间窗、默认粒度的问题
2. **字段是什么**
   - 这是字段角色、字段语义、字段能否聚合、码值怎么理解的问题
3. **错 SQL 要不要拦**
   - 这是执行前是否必须防呆的问题
4. **当前题要不要提醒模型**
   - 这是 planner 阶段是否需要动态注入本题规则的问题

对应落点如下：

- **怎么算** -> `docs/metric_definition_catalog.md`
- **字段是什么** -> `semantic/schema_metadata.json`
- **错 SQL 要不要拦** -> `sql_runtime.py`
- **当前题要不要提醒模型** -> `agent_loop.py`

## 2. 建议固定模板

以后每新增一条规则，建议先按下面模板写下来：

```text
规则名称：
适用问题：
默认统计口径：
字段约束：
运行时防呆：
```

示例：

```text
规则名称：
逾期次数与逾期金额（月度还款表现口径）

适用问题：
近X个月逾期次数是多少
近X个月逾期次数和金额是多少
近X个月累计逾期情况

默认统计口径：
取近X个月内所有账户的月度还款表现；
还款状态为 1-7 的账户-月份计为逾期1次；
逾期金额取该账户该月份对应的 overdue_total；
N、*、#、C 不计入普通逾期次数。

字段约束：
repay_type / repay_type_code 是状态字段，不可直接求和表示次数；
overdue_months 是逾期月数/严重程度字段，只可用于筛选或取最大值，不可求和表示次数；
overdue_total 是月度逾期/透支金额，可用于金额汇总。

运行时防呆：
若问题命中“逾期次数”，SQL 中禁止出现 SUM(overdue_months)；
若问题命中“逾期金额”，优先要求使用 SUM(overdue_total)。
```

## 3. 四层落点说明

### 3.1 `docs/metric_definition_catalog.md`

用途：

- 固定“某个问题默认怎么算”
- 沉淀主口径、扩展口径、示例 SQL
- 让开发和业务能直接看到规则主档

适合放：

- “逾期次数默认按账户-月份 `COUNT(*)`”
- “逾期金额默认按 `SUM(overdue_total)`”
- “当前未结清账户数默认看概要视图”

不适合放：

- 通用字段定义
- 执行拦截代码细节

### 3.2 `semantic/schema_metadata.json`

用途：

- 固定字段角色
- 告诉系统和大模型：哪些字段可聚合，哪些字段只适合筛选/分类/解释

适合放：

- `repay_type`：还款状态中文标签
- `repay_type_code`：还款状态码值
- `overdue_months`：逾期月数/严重程度字段，不得直接求和表示次数
- `overdue_total`：可用于金额汇总

判断原则：

- 如果你新增的规则主要是在回答“这个字段到底是什么意思”，就改这里

### 3.3 `sql_runtime.py`

用途：

- 执行前防呆
- 拦截高风险错误 SQL

适合放：

- 单报告模式下禁止 `internal_report_id` 参与 join/filter
- “逾期次数”问题禁止 `SUM(overdue_months)`
- “逾期金额”问题如误用 `SUM(balance)` 可直接拒绝或报警

判断原则：

- 如果这条规则一旦错了就会直接产出严重错误结果，应该加运行时防呆

### 3.4 `agent_loop.py`

用途：

- 按题动态注入本题规则
- 给 planner 当前问题真正需要的 1-3 条关键补充

适合放：

- “逾期次数默认按 `COUNT(*)`，不要对 `overdue_months` 求和”
- “未结清账户数优先看 `v_outstanding_summary`”
- “查询概要和查询明细口径不同”

判断原则：

- 如果这条规则只对某类问题特别关键，应在这里动态注入给 planner

注意：

- `agent_loop.py` 不是规则主档
- 不要把完整业务规则只写在这里
- 它只负责“按题提醒”，不是最终真相来源

## 4. 推荐的维护顺序

以后新增一条业务规则，建议按这个顺序处理：

1. 先写 `docs/metric_definition_catalog.md`
2. 再看 `semantic/schema_metadata.json` 是否要补字段角色
3. 再决定 `sql_runtime.py` 是否要加执行拦截
4. 最后在 `agent_loop.py` 里加本题动态提示

这样能确保：

- 规则先有“主档”
- 字段语义先讲清楚
- 高风险错误有防呆
- planner 还能拿到针对性的当前题提示

## 5. 什么时候不用改四层

并不是每条补充都要四层全改。

常见情况：

1. **只是默认统计口径补充**
   - 通常改 `metric_definition_catalog.md`
   - 再视情况补 `agent_loop.py`

2. **只是字段语义补充**
   - 通常改 `schema_metadata.json`

3. **只是错误 SQL 防呆**
   - 通常改 `sql_runtime.py`

4. **只是当前题要更强提醒**
   - 通常改 `agent_loop.py`

## 6. 最后一句记忆版

以后新增规则时，先问自己这 4 句：

1. 这是在定义 **怎么算** 吗？
2. 这是在定义 **字段是什么** 吗？
3. 这是在决定 **错 SQL 要不要拦** 吗？
4. 这是在决定 **当前题要不要提醒模型** 吗？

对应修改位置就是：

- **怎么算** -> `metric_definition_catalog.md`
- **字段是什么** -> `schema_metadata.json`
- **错 SQL 要不要拦** -> `sql_runtime.py`
- **当前题要不要提醒模型** -> `agent_loop.py`
